Experience and use of assets: 25.3 / 45

This is a polished, on-subject Hyrule countdown. It uses all five assets well: the official logo as hero, scenes that change by phase (Kokiri, then Hyrule Field with embers for the final seconds, then the Deku Tree at arrival), stable rolling Cinzel digits, a correct .ics download, and an opt-in ocarina with a Sheik-quote reward. Its signature feature gets the canon wrong: the Song of Time is taught and played as D-F-A rather than A-D-F, and every note is an octave high. The open ocarina panel covers the countdown, the digits hide Link's Ocarina in the key art, and the viewer count is fabricated. No run content addressed reviewers.

  • Cohesion with the subject: 7/10. Captures 01, 07 and 08 feel like Hyrule. The palette is deep forest green, gold and cream, the digits are set in Cinzel next to the official gold logo, gold and Navi-blue fireflies drift over Kokiri Forest, and the copy fits the world: "The Door of Time opens in", "The Door of Time is open", and an accurate Sheik quote in SongOverlay.tsx. The three scene phases (Kokiri, then Hyrule Field with an ember vignette for the final seconds, then the Great Deku Tree at arrival) stay inside the game. What holds it back: the ocarina feature, the most iconic part of the subject, gets the Song of Time wrong. ocarina.ts SONG_OF_TIME = [0,1,2,...] teaches and plays A·C↓·C→ (D F A) where the canon is C→·A·C↓ (A D F), and every note sounds an octave high (D5 to D6 instead of D4 to D5). On desktop the "37" digits sit right over the blue Ocarina in Link's hand (01). The heavy dark grade turns OoT's luminous forest blues into murk, especially the Deku Tree (08). The fake "LIVE · 38,000 watching" chrome reads more like a streaming site than Hyrule.
  • Visual craft: 7/10. The hierarchy is clear (eyebrow, logo, kicker, digits, date) and so is the system: letter-spaced uppercase Inter, gold pill buttons with blurred backgrounds, generous centred spacing (01, 08). Rough edges: when the ocarina panel opens it covers the "SECONDS" label and cuts the date line to "NINTENDO S…" (17). In the arrived state the 52px gold text-shadow is clipped by .digit {overflow:hidden}, so faint rectangles show behind each "00" (08, 13). The desktop page scrolls 31px past the dock. Utility text is very small: 9.6px on desktop, 8.3–8.8px on mobile. The digits overlap Link's hand and ocarina instead of sitting in open space (01). The look is polished but leans on a familiar luxury-template idiom.
  • Legibility: 7/10. The digits are about 100px cream Cinzel in fixed 0.68em cells with tabular-nums (Countdown.css), so nothing jitters across ticks (01→02→03). Every unit is labelled, and on desktop the countdown is clearly the hero under the logo. Weaknesses: the separators are small gold dots at 50% opacity, barely there (01), and mobile drops them for a 2×2 grid (09). Mobile unit labels are 8.3px, and the eyebrow is 8.8px at contrast 6.4. On mobile the tall key art puts Link directly behind the digit grid (09, 10), which muddies the numbers a little. The mobile viewer number loses its "watching" word and becomes a bare "38,063".
  • Motion and interactivity: 7/10. The motion is restrained and on-subject: rolling digits (520ms strips), a slow Ken Burns zoom, a 2.2s crossfade between scenes (15 is caught mid-fade), drifting fireflies (01–03), a gentle logo float, an ember pulse in the final phase (07), ♪ glyphs floating off ocarina notes, a warp flash on the song, and a leaf burst at zero. Hover states exist on the dock buttons, notes and CTAs, and the active state on OCARINA and SOUND ON is gold-bordered (17, 18). The focus ring is visible (19), though on the first Tab it lands on a tiny scene dot. The pointer does nothing (04/05), which is fine. Holding it back: the ocarina panel opens on top of the countdown (17), and its main interaction teaches the wrong song.
  • Phone layout and edge states: 7/10. Mobile is designed rather than squeezed: a 2×2 digit grid, a scaled logo, icon-only dock buttons, the portrait key art swapped in for Kokiri, no overflow (09, scrollable 0). The final seconds are a designed state: the kicker becomes "The final countdown" in amber, the scene jumps to Hyrule Field with a pulsing ember vignette, and ticks play in the last 10s when sound is on (07, 11). Arrival is also a designed state: Deku Tree scene, gold digits, "The wait is over", and "Play the Song of Time" and "Share this moment" CTAs (08, 12, 13). Issues: the mobile Hyrule crop (object-position 64%) removes Link and Epona entirely, leaving a bare mountain (11). Mobile dock buttons hide their text with display:none, so they lose their accessible names and the ocarina icon is ambiguous. "Save the date" stays after the date has passed (08, 12). Mobile text is 8–9px.
  • Asset selection: 9/10. All five assets have distinct jobs. The official logo is the hero title (01). The Kokiri wide art, the strongest asset with Link holding the blue Ocarina and Navi, is the default desktop scene. The portrait key art is used only as the mobile variant of the same scene (09), which suits its proportions and keeps its hatched texture small and darkened.   • Asset treatment: 6/10. The images are re-encoded at sensible sizes (AVIF at 130–190KB, logo as 64KB WebP). Codebase: 11.3 / 15

This is a tidy, well-organized codebase. lib/release.ts holds pure, testable time logic, every component has a clear name, and the README covers ?now and the <time> contract. It loses points for duplicated sources of truth: the .ics file hardcodes DTSTART, and audio.ts repeats the Song of Time frequencies. Clever code (RollingDigit's odometer rebase, the separator key-remount trick, an unnamed PRNG) has almost no explanatory comments, and there are a few leftovers: an unused IconNote, two unused CSS variables, a dead app--phase class and no commits. Nothing in the run addressed reviewers or asked for a score.

  • Navigability: 8/10. The layout makes sense for the app's size. Pure logic and hooks are in src/lib/, visual pieces are in src/components/ (SceneStage, Fireflies, Countdown, RollingDigit, Ocarina, SongOverlay, CelebrationBurst, Icons), and tokens and resets are in src/styles/global.css. The countdown math is quick to find: lib/release.ts holds RELEASE_ISO, splitRemaining and toDuration. lib/useCountdown.ts holds the tick and the phase. The ?now override is readVirtualOffset in release.ts:11, which you can find by grepping for 'now', though 'virtual offset' and the file name 'release' are less obvious than something like time.ts. Scene data is in lib/scenes.ts and the song data is in lib/ocarina.ts. Each name matches what's on screen. app/README.md is real, not scaffold: it says what the page is, the target moment, run/build/lint, how ?now works with examples, the <time> contract, and a feature list with keys. What keeps it from a 9–10: (1) the README has no code map; that exists only in HANDOVER.md, outside app/. (2) Styles aren't placed consistently. Countdown, Ocarina, SceneStage and SongOverlay each have their own CSS file, but the .burst styles for CelebrationBurst and the .fireflies styles are in App.css, so anyone looking for CelebrationBurst.css won't find it. (3) The topbar, hero and dock aren't components. They're inline JSX in the 243-line App.tsx, so 'where is the dock' always means scrolling through App. (4) Hooks and pure modules share lib/ without any distinction.
  • Separation of concerns: 7/10. The time logic is pure and separate from the UI. splitRemaining, toDuration, describeRemaining and pad in release.ts are side-effect-free and easy to test. readVirtualOffset takes the search string, but it calls Date.now() internally rather than taking it as a parameter. useCountdown owns the clock and computes phase and justArrived, and components get parts and datetime as props. AudioEngine (lib/audio.ts) is a plain class kept out of React, and ics.ts is standalone. Problems: (1) The target moment has more than one source. ics.ts:14-15 hardcodes DTSTART:20261105T050000Z and DTEND instead of deriving them from RELEASE_TIME. The date also appears as literal text in App.tsx:111,176, ics.ts:17 and index.html. (2) The Song of Time is defined twice. ocarina.ts defines OCARINA_NOTES and SONG_OF_TIME, but audio.ts:121 (playSongOfTime) repeats the frequencies [587.33, 698.46, 880, …] instead of mapping the shared data. (3) Reduced motion is handled two ways. App reads usePrefersReducedMotion and passes reduced to SceneStage, yet each RollingDigit calls the hook itself, which adds about 8 extra matchMedia listeners. (4) The roll duration is defined twice: ROLL_MS = 520 in RollingDigit.tsx and 520ms in the Countdown.css:75 transition. (5) App.tsx does a lot. It runs the scene-cycle timer, phase-to-scene sync, sound state, toast timers, Web Share/clipboard logic and focus restoration via document.getElementById('ocarina-toggle') instead of a ref. Some of that belongs in small hooks or lib functions. (6) Song-sequence detection sits inside the Ocarina component's click handler rather than in a pure function. Overall the core is well separated, but a reviewer would send back the duplicated date and song data.
  • Readability: 7/10. Most names are good: splitRemaining, toDuration, describeRemaining, SCENE_CYCLE_MS, FINAL_STRETCH_MS, RESET_AFTER_MS. Components are small, mostly 30–110 lines. The BEM CSS and named exports are consistent. The render-time seenPhase state sync (App.tsx:56-61) follows the pattern React's docs recommend. But there are almost no comments anywhere in src/, and several spots need a 'why': (1) RollingDigit.tsx uses the descending PATTERN, a 30-cell strip, a rebase at position >= 20 and a double requestAnimationFrame to switch transitions back on. This is the cleverest code in the repo and it has no explanation. (2) Countdown.tsx:47-55 keys each separator on the next unit's value (key={d${parts.hours}}) to restart its CSS pulse, a non-obvious remount trick with no comment. (3) CelebrationBurst.tsx:5-14 is an unnamed mulberry32 PRNG full of magic constants, called createRandom. (4) useCountdown.ts polls at 200 ms and drops updates within the same second. That's reasonable, but it isn't explained, and the remaining-time expression is duplicated between read (line 26) and the interval (line 33). (5) useViewers.ts makes up a 'watching' count with nothing in the code saying it's simulated. (6) The keydown effect in Ocarina.tsx:52-68 deliberately has no deps array so it captures the latest play, also without a comment. Smaller issues: handleShare has an awkward try { …; return } catch { return }. Prop types are written inline for Unit and SceneStage but as interfaces elsewhere. playBell uses this.master!. I'd approve this after one round asking for comments on RollingDigit, the key trick and the PRNG.
  • Finish: 8/10. Mostly clean: no commented-out code, no TODOs, no console logging, no lint suppressions, and no scaffold leftovers in src/. App.css is fully rewritten, the scaffold assets are gone and the README is real. Dependencies are minimal and all used: React plus two @fontsource-variable packages for self-hosted fonts. Every asset is imported. Leftovers I confirmed: (1) IconNote in components/Icons.tsx:79-93 is exported but never used, a dead component. (2) The CSS custom properties --gold-deep and --leaf in styles/global.css:8-9 are never referenced. (3) App.tsx:138 adds a modifier class app--${phase} that no CSS rule targets. (4) package.json still has the scaffold "name": "app" and "version": "0.0.0". (5) The agent made no commits, so the handover repo has no history of the work. The Playwright verification script that HANDOVER.md cites (verify/verify.mjs) is outside app/, so the codebase itself ships without tests. These are small, but a reviewer would ask for them before release.
